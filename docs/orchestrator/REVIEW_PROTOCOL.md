# Human review and recommendation protocol

모든 사람 리뷰는 Coordinator 한 곳에서 취합한다. Worker가 서로 다른 채널로 선택을 요구하지 않는다.

## 사람에게 올릴 항목

- 안전 기준 완화, 제품 범위 변경, 이미 공유된 API의 호환성 변경.
- 추가 지출·구독·외부 공개·배포 등 현재 지시로 허용되지 않은 결정.
- 구현된 브랜치의 main 통합 전 실제 diff/검증에 대한 사람 리뷰.
- 계약으로 해결할 수 없는 사용자의 선호 또는 서로 배타적인 제품 방향.

이미 허용된 구현의 내부 파일 구성·timeout·복구 가능한 버그 수정 등은 자율적으로 해결하고 기록한다.
사람 리뷰를 위한 자료는 먼저 완성한다. 연구·코드·diff·검증 없이 추상적인 승인만 요청하지 않는다.

## 선택지 제시 전 외부 조사

1. 결정 질문과 현재 제약(7시간 MVP, Android+FastAPI, 장비 안전, PC 구성)을 정의한다.
2. 공식 문서, 제조사 매뉴얼, 유지되는 공식 샘플/오픈소스 구현에서 선례를 찾고 실제 페이지를 연다.
3. 1–3개의 직접 관련 출처를 기록한다. 조회 날짜·지원 버전·적용 조건과 현재 환경 차이를 명시한다.
4. 공식 지원인지, 외부 구현 사례인지, 우리 프로젝트에서 실제 테스트를 통과했는지 구분한다.
5. 이미 검토 가능한 구현·샘플·작은 실험이 있으면 실행하고 결과를 첨부한다. 조사만 했으면 로컬 검증 미실행이라고 적는다.
6. 선택지는 2–3개 이하, 추천안 먼저. 구현 시간·비용·호환성·위험과 복구 방법을 비교한다.
7. 추천 이유와 근거 링크, 남은 불확실성을 짧게 설명한다. 선례가 없으면 없다고 기록하고 검증된 척하지 않는다.

기본 추천 형식:

```text
결정: <구체적 질문>
추천: A — <현재 상황에서 적합한 이유>
근거: <직접 페이지 링크와 확인 날짜>
검증: <실행한 명령/결과 또는 미실행>
선택: A <영향> / B <영향>
리뷰 자료: <branch, commit, diff 또는 문서 경로>
```

필요한 질문은 비동기 사용자 입력으로 올리고 독립 작업을 계속한다. 답변 전 해당 승인에 의존하는 동작은 하지 않는다.
결과는 `docs/reviews/<id>.md`에 pending/approved/rejected와 승인자의 실제 응답을 남긴다. 검토 자료만으로 승인했다고 기록하지 않는다.
승인된 결정은 `docs/decisions/`에 옮겨 관련 Worker에게 알린다. 사용자 지시는 사전 문서의 승인 규정보다 우선한다.
